# 持久会话的一次性启用决定

2026-10-14。实现已随 #40 合并，审查 HEAD `546bb58a61945a68b7a03bd6bd5f13ffdca81ea0`，main `b025714dcd9da63597deb9756cf47cdfc5225916`。10 个浏览器入口及真实产品协议通过；没有未解决的会话 P1/P2。当前生产模式尚未核实、也未由本任务启用。legacy 模式仍有迟到 Cookie 响应风险，代码部署本身不能声称修复生产问题。

## 建议一次决定的范围

批准为指定 Pages 生产项目启用持久会话：先核实当前项目和数据库绑定，在隔离环境验证真实 D1 和浏览器，再创建或选定一个空的专用会话库、初始化 schema 和收据签名密钥、绑定 `MISUB_SESSION_DB`，最后设置 `SESSION_AUTH_MODE=d1-v1` 并部署；接受所有现有管理员会话强制重新登录一次。任一步核验不通过即停止在该阶段，已初始化专用库保留用于核查，不删除数据或自动回退接受旧 Cookie。

实际账户、Pages 项目、会话数据库 ID 尚待通过既有管理会话只读核实，不能猜测或把 CI 名称当作授权目标。若批准该范围，目标核实不必另问普通代码授权；与目标不符或需要额外权限时才升级说明。

| 操作                                                       | 是否新增安全敏感动作                 | 实际影响                                                                                                   |
| ---------------------------------------------------------- | ------------------------------------ | ---------------------------------------------------------------------------------------------------------- |
| 选择已存在的空专用 D1                                      | 选择本身为只读，但绑定及初始化仍敏感 | 必须与业务、Probe、登录审计库 ID 各自不同；未知或非空库不直接初始化                                        |
| 没有合适库时新建专用 D1                                    | 是，新增生产安全资源                 | 只存会话状态，不迁移订阅、设置或 Probe 数据                                                                |
| 执行 [session-authority.sql](schema/session-authority.sql) | 是，DDL 和初始行写入                 | 创建一个会话表及唯一状态行；应用运行时不会自动创建它                                                       |
| 初始化 receiptKey                                          | 是，生成新的签名秘密                 | SQL 使用 `randomblob(32)` 生成，保存在专用库；不输出正文，不修改现有管理员密码、COOKIE_SECRET 或检测器凭据 |
| 增加 MISUB_SESSION_DB 绑定                                 | 是，应用获得会话数据库读写权限       | 自动部署脚本只保留已有合法绑定，不能借 CI 输入完成首次授权                                                 |
| 设置 SESSION_AUTH_MODE=d1-v1 并部署                        | 是，改变认证权威和会话有效性         | 全部旧 `auth_session` 不再授予管理权限；每个管理员浏览器需要重新输入既有密码                               |
| 实际登录/退出验收                                          | 是，写入新库的合成或指定验收会话     | 只调用会话端点并记录状态码/脱敏计数；不以生产 `/api/data` 作为测试请求                                     |

独立登录审计 `MISUB_SECURITY_DB` 的创建/初始化/启用不是修复 Cookie 所必需。本次会话决定不自动批准它，也不包含业务事务模式、订阅迁移、管理员密码轮换或故意触发生产 IP 锁定。若审计已启用，则沿用并验证与会话准入的已有组合约束。

## 会话范围和用户影响

- 首次从 legacy 切换不能安全保留旧签名 Cookie 的权限；必须强制重新登录。继续信任旧 Cookie 会保留同一漏洞。
- 启用后的普通退出撤销当前浏览器在 capture 中证明并固定的 SID/票据及共享登录意图，不是全设备退出。其他独立浏览器的会话保留。
- 新登录先创建 pending SID，再确认浏览器实际收到 Cookie；确认成功才撤销固定旧目标。失败或提交结果不明不提前撤销正常旧会话，也不发放可用新权限。
- 有效会话空闲 30 天、最长 90 天；续期只更新数据库。退出失败保留恢复记录并阻止静默恢复登录，用户可重试。

## 启用顺序与停止点

1. 只读核实目标、当前部署和全部数据库 ID；确认现有密码认证可由用户正常使用，但不读取或导出密码/Cookie。
2. 在隔离的真实 Cloudflare D1/预览环境运行同一准确源码，验证 first-primary/CAS、缺绑定/故障拒绝、迟到 login/续期/logout、多标签和失败重试。该阶段也需要独立测试资源授权。
3. 在批准的生产专用库初始化一次，仅核对表、schema、revision、空集合数量和密钥存在/格式；不输出密钥。记录不含秘密的资源 ID 和部署 SHA。
4. 加绑定后保留 legacy，验证部署保护能正确保留该绑定；确认测试与恢复通道就绪，再切换模式并部署。切换期间旧部署仍可能完成 legacy 响应；只有新模式下服务端拒绝旧 token 才可视为撤销边界生效。
5. 使用指定浏览器做一次受控重新登录/退出及重载验收，只记录 `protocol`、认证布尔值、状态码和脱敏数量。生产接口不能用来注入故障或主动触发锁定。
6. 记录真实 D1、浏览器和部署证据后才能把生产 Cookie 修复标为完成；其他浏览器（如 Safari）缺测单列。

## 故障与恢复

切换前失败可保持 legacy 并保留未启用的新库，旧漏洞仍明确存在。切换后存储不可用会拒绝管理鉴权，允许出现受控管理登录中断；不能自动回退到 legacy。优先前向修复并保持 d1-v1，所有会话密钥和撤销历史保留。

旧数据库快照可能恢复已撤销 SID。若必须恢复，需单独批准使所有旧 SID 失效并强制重新登录；仅轮换 receiptKey 不够。不得直接覆盖旧备份、删除会话库或重新开放旧 token 兼容。已有业务数据和业务绑定在整个会话启用流程中保持原有权威来源。
