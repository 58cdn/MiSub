# 订阅编辑与保存响应

关联 [Issue #33](https://github.com/58cdn/MiSub/issues/33)。本功能保护单个浏览器数据仓库中的加载、编辑和保存响应。

## 完整加载与保存基线

`/api/data` 必须同时包含 `misubs`、`profiles`、`ruleTemplates` 三个对象数组和 `config` 对象。订阅和订阅组的 ID 必须是非空字符串，且各集合内唯一。完整的空集合是合法响应。缺失字段、错误集合类型、空行、失败标记或不可序列化的数据不能替换编辑区。所有集合先校验、深克隆，再发布到仓库；失败保留原数据、已确认快照、缓存和待保存状态。

包含重复 ID 的响应需要先核对数据，前端不会自动去重并据此授予保存基线。如果后端已将重复 ID 合并后返回，前端无法察觉被合并的行；这仍属于存储完整性调查范围。

成功的服务器读取或认证初始化注入完整响应后，才建立保存基线。会话缓存可先展示，但仍须完成服务器加载；只读到缓存而服务器加载失败时，`saveData` 不发送保存请求，节点也不能因缓存记录而标成已保存。缓存本身不是服务器版本。

已有完整基线时，后续刷新失败保留该基线和当前编辑，仍允许用户保存。此基线只代表此前完整加载过的数据，不证明它仍是服务器最新状态；另一个客户端的修改仍可能发生冲突。清除会话缓存会撤销保存基线，后续必须重新完整加载。

## 保存与继续编辑

提交时对订阅及订阅组深克隆，并在提交副本上清理无效引用、归一化旧规则字段。失败不改变编辑区中的引用。只有 `success: true` 且同时返回完整订阅、订阅组数组时才确认保存；缺失或非法的成功响应按失败处理，不能据此清除待保存状态。

保存响应更新的是服务器确认快照和缓存。发出请求之后的新增、修改、删除、排序、嵌套编辑，以及额外的 `markDirty` 调用均保留在编辑区，继续待保存；直接通过响应式引用修改数据也会在响应处理时检查。没有后续编辑时，编辑区采用服务器归一化后的结果并清除待保存状态。节点是否已保存以确认快照中的 ID 和 URL 为准，不能因当前编辑区新增了节点就将其标成已保存。

保存订阅时不会把当前未确认的规则模板或设置写入缓存；这些字段保留各自最近确认的值。保存响应失败不能证明服务器没有发生写入，用户仍需核对结果。

## 请求交错与会话边界

- 同一时刻的两次刷新共用一个请求，保存期间不启动刷新或第二次保存。
- 主动刷新可以丢弃刷新开始前的编辑；刷新开始后的新编辑继续保留，刷新返回失败并提示用户。
- 新的权威数据注入或清除会话缓存会使旧加载、保存响应失效。失效响应不能改写快照或缓存，也不能清除待保存状态。
- 旧请求结束前保持操作锁，结束后才启动下一请求。成功提示的定时状态复位不会重置较新保存的状态。

## 验证和限制

离线回归使用合成数据和受控 Promise，覆盖完整及异常加载、缓存权限、无基线保存、各类保存中编辑、失败及残缺成功响应、重复保存、刷新交错、会话清理和正常成功。测试不访问生产接口或真实订阅。

前端无法识别服务器将读取异常伪装成合法空数组的情况，因此依赖 [PR #41](https://github.com/58cdn/MiSub/pull/41) 的权威读取错误契约。跨客户端旧快照、Cron/Telegram/API 并发写入、集合事务和写入中途失败，仍需服务端统一版本与事务协议；本功能不提供 CAS 或回滚保证。生产完整性调查、部署与配对冻结保持有效。
