# 订阅原子写入：离线模型与迁移门槛

关联 [Issue #33](https://github.com/58cdn/MiSub/issues/33)，依赖 PR #37、#41、#42。本文细化[版本与迁移协议](subscription-write-protocol.md)，记录 PR #43 的独立离线模型。[SQL 模型](../experiments/subscription-transactions/model.js)仅由测试导入；默认关闭的应用接入、能力限制和迁移门控见 [PR #44 运行时约定](subscription-runtime-contract.md)。生产 schema 不会自动启用。

## 后端选择

| 后端                     | 现有结构                                                          | 原子协议所需改造                                                                | 本轮交付                               |
| ------------------------ | ----------------------------------------------------------------- | ------------------------------------------------------------------------------- | -------------------------------------- |
| 已绑定业务 D1            | subscriptions/profiles JSON 行，可能混有 id=main 旧数组；settings | 规范化业务行，持久 epoch/revision、历史 epoch、收据和事务准入；全部 writer 转换 | SQLite 与本地 Miniflare D1 的 SQL 模型 |
| KV-only                  | 两个独立集合键，最终一致                                          | 选择业务 D1 或 Durable Object 作为唯一权威存储；未具备时严格模式拒绝写入        | 能力拒绝测试，未实现 KV CAS            |
| 未初始化、缺失或错误绑定 | 无可验证的权威版本                                                | 经受控初始化建立存储身份和首个 epoch                                            | 拒绝提交，不自动初始化或降级           |

D1 `batch` 按序执行 SQL，任一语句失败会回滚整个序列。版本门槛必须触发 SQL 错误，不能只依赖条件 UPDATE 影响零行。[D1 batch](https://developers.cloudflare.com/d1/worker-api/d1-database/#batch) KV 不提供这里需要的跨集合原子事务，写前重读或进程内锁不能替代权威提交点。[KV 一致性](https://developers.cloudflare.com/kv/concepts/how-kv-works/)

复用已有业务 D1 可以避免新建数据库，但仍涉及 schema、历史数据迁移和部署切换。KV-only 选择 Durable Object 则还需设计其存储、接口、迁移和绑定；本模型不能证明 DO 实现。Probe 库和安全登录库不承载这些业务集合。

## 已实现的 SQL 内核

`compileSnapshotCommit` 接收**服务端准备好的候选快照**，不是可直接开放的 HTTP 全量保存接口。编译前检查 JSON 容量、集合大小、稳定且唯一的 ID、组引用和版本格式，生成绑定参数与规范化 SHA256。它只接受 `backend: 'd1-model'`；运行时 `d1`、`kv`、`noop` 均被拒绝。

模型表全部使用 `model_` 前缀：

| 表                       | 责任                                                              |
| ------------------------ | ----------------------------------------------------------------- |
| meta                     | 唯一的当前 epoch 与非负安全整数 revision                          |
| epochs                   | 永不复用的历史 epoch；初始化也登记，即使该代没有收据              |
| subscriptions / profiles | 同一事务中的两个业务集合                                          |
| receipts                 | epoch、操作 ID、摘要、确认版本和条目计数，不存原始 URL 或节点凭据 |
| gate                     | 当前事务的准入记录，校验版本、重试摘要与容量                      |
| gate_seal                | 始终为空的约束目标；gate 的延迟外键要求事务提交前完成关闭         |

同一个 D1 `batch` 包含九条预编译 SQL；测试也将同一组 SQL 放入真实 SQLite 事务：

1. 插入 gate，触发器检查初始化、当前 epoch、操作摘要、revision、历史 epoch 和容量。新操作 `apply=1`，当前 epoch 已提交的相同请求 `apply=0`。
2. 删除待替换的订阅行，仅在 `apply=1` 时执行。
3. 从绑定 JSON 插入候选订阅行，同样受 gate 约束。
4. 删除待替换的组行。
5. 插入候选组行。
6. 推进版本；普通提交 revision 加一，恢复切换到未出现过的 epoch 并设 revision 为零。触发器在同一事务登记新 epoch。
7. 插入非敏感收据。
8. 关闭 gate；关闭触发器要求确认版本和收据一致。
9. 返回收据。

业务表 INSERT/UPDATE/DELETE 必须有本事务 `apply=1` 的 gate。未关闭 gate 的截断 batch 因延迟外键失败，提前关闭因版本/收据不完整失败，错误都会回滚。测试显式确认 SQLite 和本地 D1 外键已启用；平台的外键及 pragma 行为见 [D1 SQL](https://developers.cloudflare.com/d1/sql-api/sql-statements/)。这套约束用于模型协议与已枚举的旧 DML，不构成对任意数据库管理 SQL 的权限隔离：具有直接数据库写权限的调用者仍可修改元数据、历史或约束目标。生产必须移除通用写入旁路并限制管理路径。

`MODEL_READ` 用一条 SQL 返回两个集合和版本，避免多个独立查询拼接不同快照。两个独立 SQLite 连接以及并发的本地 D1 batch 验证同基线只允许一个新操作成功；没有使用 JavaScript 锁模拟数据库原子性。

普通请求响应丢失时，相同操作 ID/摘要可取得原收据，不重复写入，也不要求旧 revision 仍为最新。恢复后旧 epoch 请求统一冲突，包括恢复请求本身的旧基线重试；调用方需要重新读取并对照目标 epoch/收据确认结果，不能重新提交旧快照。恢复不能指定当前或任意历史 epoch，失败事务中的 epoch 登记随同回滚。

## 从内核到应用协议

以下仍是待实现接口，模型没有 HTTP 路由、认证处理器、显式操作解释器或 writer 接线：

```json
{
    "operationId": "unique-operation-id",
    "baseVersion": { "epoch": "current-history-id", "revision": 12 },
    "operations": [
        {
            "type": "update",
            "collection": "subscriptions",
            "id": "stable-id",
            "fields": { "name": "新名称" }
        },
        { "type": "remove", "collection": "subscriptions", "ids": ["explicit-id"] }
    ]
}
```

服务端鉴权后，从同一权威快照解释 create/update/remove/reorder/link/unlink，校验字段白名单、ID 冲突与引用，生成候选状态。最后的原子 gate 必须再次核对该快照版本；期间发生其他写入就整体拒绝。不能把客户端全量快照的缺项当作删除，也不能给无基线旧请求补上服务器当前版本。

| 响应                      | 调用方行为                                       |
| ------------------------- | ------------------------------------------------ |
| 200/201，确认版本及收据   | 只确认提交时编辑；后续本地编辑继续保留           |
| 409，revision/epoch 冲突  | 保留编辑，重读完整快照并呈现差异，不自动覆盖重试 |
| 409，operation_id 冲突    | 同一 ID 对应不同摘要，停止重试                   |
| 428，version_required     | 旧客户端刷新/升级；不执行业务写入                |
| 503，存储或原子能力不可用 | 保留本地编辑，不切换到 KV 或空存储适配器         |

数据库错误到 HTTP 的映射还未实现，须使用固定错误码，不能把原始 SQL、绑定参数或存储异常返回给用户。运行时读取也需明确 primary/session 起点，不能把本地 D1 验收等同实际平台跨 isolate 验收。

## 全部 writer 的接入要求

[完整源码盘点](subscription-writer-inventory.md)固定在 PR #42 `ed662e2`，列出文件、函数、现有持久化方式及转换要求，包括条件触发和旧代码路径。接入范围为：

- 网页全量/diff 保存、单源和批量刷新、文本/文件导入；普通导入是明确 create，恢复是单独流程。
- Cron、手工 Cron、节点计数、订阅下载 waitUntil 回写。网络请求在事务外，结果绑定稳定 ID、开始时 URL/请求配置身份及观察时间；提交时重读当前状态、只合并运行字段并有限重试。删除或身份改变后拒绝旧结果，UPDATE 不得 UPSERT 复活记录。URL 本身可能含凭据，指纹也不能成为公开日志内容。
- 外部订阅、手动节点和组的 CRUD、链接/解绑、刷新及会触发节点计数回写的 validate 路径。
- Telegram 命令、文件/文本导入、回调操作。回调须改用稳定 ID 和原视图版本；数组序号即使搭配写时 CAS 也可能指向错误记录。事件 ID、明确意图和当前权限共同参与去重。
- 恢复、在线迁移、管理 GET 和公开下载中的自动 profile ID 迁移。正常读取应无业务迁移副作用；旧 main 写入旁路必须关闭。
- 普通 settings 保存、重置、备份恢复中的 storageType 修改。权威存储身份必须固定在受控配置中，不能由可变业务设置或进程级设置缓存选出另一份可写历史；错误绑定与读失败必须拒绝，禁止回落到旧 KV。

通知应在提交确认后发送。若需要可靠投递，需另行实现事务内 outbox 和幂等消费；事务成功不等于外部消息 exactly-once。下载计数、节点缓存、日志、Probe、安全库以及备份里的规则/设置不在本模型的双集合事务域，不能对整个应用宣称原子恢复。

## 模型容量与未覆盖部分

模型把候选 JSON 限制为 256 KiB，每集合最多 1000 条，所有 epoch 合计最多 128 个收据。收据不自动回收；满后拒绝新写入和恢复，已提交的当前 epoch 重试仍可读取原收据。历史 epoch 永不回收。这个容量策略用于验证拒绝语义，不是可用的生产容量方案。

九条 SQL 采用少量绑定参数和 JSON 展开，便于一次提交；它仍会重写两个有界集合。未来实现必须结合实际 D1 的参数、语句、数据和请求限制测量资源用量，超限拒绝或另行设计分代数据加原子指针，不能分成多次提交后仍称整体原子。[D1 限制](https://developers.cloudflare.com/d1/platform/limits/)

当前测试覆盖事务失败、并发准入、收据重放、摘要冲突、旧 DML 拒绝、gate 截断/提前关闭、epoch 永不复用和失败恢复回滚。尚未覆盖实际应用显式操作、运行时字段合并/指纹、所有 writer 接入、旧 main 数据迁移、收据生命周期、备份多域协调、实际 Cloudflare 多 isolate 行为与生产负载。Miniflare 是本地 D1 引擎验收，不是实网部署验收。

## 迁移方案与专项批准边界

本轮提供可执行离线模型和 writer 清单，没有生产迁移执行器，也不在首次请求上创建 schema。后续可以继续用合成数据实现显式操作、全部 writer 集成和迁移演练；实施生产变更前必须明确批准以下内容：

1. 选择实际业务权威存储。已有 D1 需批准目标库的 schema/数据转换；KV-only 需先选 D1 或 DO，确认所需资源与绑定。Probe/安全库不复用。
2. 指定私密备份位置和维护窗口。直接读取源物理 `id,data`，分别盘点 main 数组与独立行，保留来源证据；同 ID 异内容、坏 JSON、悬空引用或业务 ID 为 main 的歧义必须停止，不使用 getter 去重后的结果猜测。
3. 阻止并排空所有旧部署 URL、API、Cron、Telegram 和在途 waitUntil/网络任务。停触发不等于排空；旧部署仍可读旧库或写旧表时，不得宣布只有一个权威入口。
4. 在维护冻结中核对源摘要、转换业务行、建立新存储历史与门槛、回读验证，并确认所有新 writer 使用同一协议。模型的 `model_` 表不能简单改名前缀后作为生产迁移运行。
5. 旧客户端无版本请求拒绝；设置保存/重置/恢复不能切换权威实例。解除冻结前验收引用、排序、runtime 回写、通知和旧 writer 拒绝行为。
6. 批准回退条件和数据处理。保留只读冻结，验证布局/绑定兼容和当前数据摘要后再恢复写入；不能只回退部署代码，让旧历史覆盖新提交。

schema、绑定、真实数据迁移、生产排空、切换和回退都需专项批准。本地测试与草稿 PR 的通过不能替代这些批准或生产验收。
