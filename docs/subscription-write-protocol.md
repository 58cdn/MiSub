# 订阅写入版本与兼容迁移设计

关联 [Issue #33](https://github.com/58cdn/MiSub/issues/33)。本文记录协议目标与迁移设计；默认关闭的 D1 实现及其实际支持边界见 [PR #44 运行时约定](subscription-runtime-contract.md)，不自动创建生产 schema、绑定或资源。[PR #41](https://github.com/58cdn/MiSub/pull/41) 处理读取失败与保存前校验，[PR #42](https://github.com/58cdn/MiSub/pull/42) 处理浏览器编辑与保存响应；两者不提供本文的跨请求事务保证。

## 一致性目标

一次变更同时覆盖订阅及订阅组引用，要么整体提交，要么保持原状。缺席于客户端旧快照的条目不能被推定为删除。刷新只写运行时字段，不覆盖名称、URL、启用、标签、排序或引用；删除后的旧刷新不能复活记录。

所有写入入口使用同一权威版本及操作协议。应用进程内锁、30 秒集合缓存、KV 写前重读、HTTP 成功状态均不作为并发安全证据。Cloudflare KV 是最终一致存储，同键并发写入可能互相覆盖；其绑定的 put 接口不提供条件版本写入。因此当前 KV 路径不能承诺全局 CAS。[KV 一致性](https://developers.cloudflare.com/kv/concepts/how-kv-works/)、[同键并发写入](https://developers.cloudflare.com/kv/api/write-key-value-pairs/)

## 协议边界

管理快照在完整权威读取成功后返回 `version: { epoch, revision }`。epoch 标识一代存储历史，revision 是该历史中的单调整数。普通编辑、事务内运行时更新与删除推进当前 revision；恢复总是建立新 epoch，并初始化该代 revision，不复用备份中的版本或幂等记录。客户端缓存只用于显示，不授予或刷新权威版本。

变更请求包含：

- `operationId`：单次操作的唯一标识，用于重试幂等；不是认证凭据。
- `baseVersion`：客户端开始编辑时的 epoch/revision。
- 明确的 `create`、字段白名单 `update`、`remove` 与 `reorder` 操作；删除必须明确列出 ID。
- 运行时更新额外绑定来源 ID 与 URL 身份指纹，仅允许流量、节点数、检测时间等预先定义字段。
- 操作的规范化摘要；幂等记录不保存节点密码、原始 URL、Cookie 或请求正文。

服务端先执行鉴权、大小限制、结构校验、重复操作/ID 校验，再在原子写入边界内验证版本与引用。创建碰撞、未知更新/删除、顺序歧义不应静默吞掉。

| 响应                        | 含义及客户端行为                                                 |
| --------------------------- | ---------------------------------------------------------------- |
| 200 / 201                   | 已提交，返回服务器确认的新版本和变更结果；只确认提交时编辑       |
| 409 `revision_conflict`     | 保留本地编辑，读取新的完整快照后展示精确冲突；不自动全量覆盖重试 |
| 409 `operation_id_conflict` | 相同 operationId 对应不同请求摘要，拒绝执行                      |
| 428 `version_required`      | 严格模式下的旧客户端缺少基线；提示刷新/升级，零业务写入          |
| 503 `storage_unavailable`   | 读取、版本或事务能力不可用；不降级到 KV/无存储适配器             |

幂等标识按实例、epoch、operationId 命名空间隔离。在当前鉴权通过后，同一原子边界内先确认请求 epoch 属于当前历史，再查已提交操作：同一摘要返回既有非敏感收据，不再次推进版本；不同摘要返回冲突。只有尚未提交的新操作才比较 base revision。如此，提交成功但响应丢失后的重试不会仅因 revision 已推进而误报冲突。恢复后的旧 epoch 重试拒绝，不能重放旧操作。

收据只含操作 ID、摘要、新版本与结果计数，不保留敏感结果正文；需要完整数据时另行鉴权读取。错误响应和日志不回显数据库正文、SQL 参数或原始异常。幂等保留期及容量在实现时明确并测试过期行为；过期重试不能自动当新操作执行，应取得新快照并重新确认，不使用“永久幂等”表述。

## D1 原子写入

建议为已有业务 D1 增加版本元数据与幂等操作记录，保持现有业务行可读取；使用同一个 D1 原子 batch 完成版本验证、操作准入、订阅/组变更、引用校验、revision 推进与结果记录。D1 batch 中任一语句失败会使整个序列回滚。[D1 batch](https://developers.cloudflare.com/d1/worker-api/d1-database/#batch)

必须让版本不匹配在事务内触发失败，不能先执行一个更新零行的条件语句，然后继续无条件执行其他写语句。实现可以用经 SQLite 与本地 D1 验证的约束/触发器准入机制；具体 SQL 与失败映射需在实现 PR 中独立审查。逐个 await、Promise.all、先读后比较都不等同此原子边界。

订阅、订阅组和 epoch/revision 必须来自同一数据库快照，可用单语句或经验证的同一只读 batch；不得拼接多个独立查询或局部缓存得到的不同版本。若采用 D1 Sessions，用 primary 或已确认 bookmark 控制读取起点；Sessions 的顺序一致性本身不代替读取快照或写入事务。[D1 Sessions](https://developers.cloudflare.com/d1/worker-api/d1-database/#withsession)

变更和恢复在写入前核对已验证的 SQL 参数、语句数与请求容量限制，无法装入原子边界时拒绝，不拆成多个提交后宣称整体原子。分代数据加原子切换指针如有需要，另行设计、审查与演练。

现有业务表不应和 Probe、安全登录库混用。本文不向 `MISUB_PROBE_DB` 或 `MISUB_SECURITY_DB` 添加业务数据，不创建新的生产库，也不修改已有绑定。

## KV 部署的选择

KV 继续作为历史数据来源或只读缓存时，写入必须由一个真正的权威存储协调。优先评估迁移到已明确选择的业务 D1；另一方案是 Durable Object 保存权威状态并统一接收写入，KV 仅作缓存。不能让多个 Worker 直接 KV 写与协调器写并存后仍宣称有全局一致性。

KV-only 实例目前无法只改本地 JavaScript 就获得跨实例条件事务。选择 D1 或 Durable Object 会涉及业务存储转换、资源/绑定或迁移授权；在授权、备份、兼容测试与切换验收齐备前，能力必须明确为未提供。禁止自动创建资源、自动切换 storageType 或在首次 GET 上迁移。

## 全部写入入口

| 入口                            | 转换方式                                                                                 |
| ------------------------------- | ---------------------------------------------------------------------------------------- |
| 网页保存、单源/批量刷新         | 明确操作 + 提交时版本；刷新操作不能携带整份旧集合                                        |
| 外部 API 的创建/PATCH/DELETE    | 编辑请求必须携带客户端基线，不替旧请求补当前版本；事务内再验证，字段合并与持久化结果一致 |
| 通知 Cron、后台定时任务         | 网络请求在事务外执行；提交运行时结果时核对 ID/URL 及当前版本；有限冲突重试重新计算字段   |
| Telegram 缓存、排序、删除、导入 | 不回写请求级整份快照；删除使用显式操作并验证实际结果                                     |
| 订阅下载、节点计数、通知标记    | 独立运行时字段操作；不得 UPSERT 已删除记录                                               |
| 备份恢复                        | 在隔离副本生成精确差异；明确删除、引用变化与新 epoch，按原子协议提交                     |
| 旧迁移路由                      | 严格模式启用前关闭旁路写入；只允许受控迁移工具，不在读取路径自动转换                     |

版本升级不能仅覆盖网页。迁移后的旧部署 URL、Cron 触发、Telegram webhook 和外部客户端也可能继续写入；必须先枚举并停用或升级所有旁路。维护冻结还须覆盖已等待网络返回的 Cron、订阅下载 waitUntil 与旧部署在途请求：停触发不等于排空任务。无法验证已排空或已阻止旧请求写入时，停止切换；若旧代码仍能写同一业务存储，严格模式不能宣布就绪。

## 旧 main 与旧客户端兼容

迁移准备阶段只做授权范围内的只读盘点：物理行数、legacy main 数组、重复业务 ID、非法 JSON、订阅组引用、实际业务绑定。报告只保留脱敏计数及摘要；真实备份和节点内容使用事先确认的私密存储范围。

1. 在隔离副本同时展开旧 main 数组和独立行。无冲突 ID 可确定性转换；重复 ID 内容完全相同可去重，内容不同必须列出冲突并停止，不采用 SQL 遍历顺序或时间戳猜测最新记录。
2. 验证 ID 稳定、组引用完整、手动节点/机场分类与排序。损坏条目不得静默丢弃。
3. 在获准的维护窗口阻止所有旧 writer 并排空在途任务，验证旧部署不能再写入，然后重新核对源摘要；无法排空或摘要变化则停止。建立私密、可验证的恢复副本，再执行 schema/数据转换。
4. 在同一受控阶段建立 epoch/revision，回读行数与规范化摘要，确认仅一个权威 writer 协议。旧 main 不再与独立行混合参与正常读取；保留的备份不是运行时数据源。
5. 严格模式启用后，无版本旧请求返回 428；不得为旧客户端自动附上“当前版本”并按旧快照删除。旧页面提示重新加载，保留本地编辑供用户比较。
6. 回退继续保持维护冻结。即使尚无新业务写入，也先证明旧程序兼容当前 schema、main 布局、绑定与 storageType，或按获准预案恢复对应布局和绑定，回读摘要确认后才恢复写入，不能仅回退部署版本。新协议已有写入后，不直接切回旧可写程序；先保持只读、导出验证后的当前状态并形成单独回退差异，避免历史重新覆盖新数据。

本方案选择明确维护窗口完成切换，避免无保护的双写期。存储迁移、资源变更、解除冻结与恢复生产均需专项批准；此设计文档不是执行授权。

## 验收矩阵与分期

- 两个客户端同一基线同时新增/更新/删除：允许一个按版本提交，另一个明确冲突；无静默覆盖。
- 订阅与组事务的每个中间语句注入失败：全部回滚，revision 与幂等记录不留半状态。
- 刷新与删除/URL 修改交错：旧结果拒绝，记录不复活，新 URL 的数据不被旧请求污染。
- 同 operationId 重试、摘要冲突、提交后响应丢失：不重复执行。
- D1 空库、旧 main、独立行、完全重复与冲突重复、坏 JSON，以及 KV-only 迁移副本分别覆盖。
- 旧网页/外部 API、Cron、Telegram、下载副作用均不能绕开版本入口。
- 跨 isolate 的独立 Worker 本地集成测试；需要实际平台确认的行为另行验收，不把内存 Map 当作分布式 KV。
- 敏感字段不出现在日志/错误/测试证据；所有默认 fixture 合成，网络禁止。
- 分期为：严格读取与本地编辑保护 → 协议及 D1 本地实现 → 全 writer 转换及迁移演练 → 专项授权后维护窗口和实网验收。已有[离线 SQL 内核与接入方案](subscription-atomic-model.md)，应用运行时尚未接入版本事务协议；模型通过不代替全 writer 转换或生产迁移验收。
